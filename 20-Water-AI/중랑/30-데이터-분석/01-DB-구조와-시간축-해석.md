# 중랑 DB 구조와 시간축 해석

## 현재 확인된 내용

### `suyo.tb_suyo`

현재 분석자료 기준 물리 컬럼은 다음 5개다.

| 컬럼 | 의미 |
|---|---|
| Num | PK / 순번 |
| TAGNAME | SCADA Tag 이름 |
| DESCRIPT | 설명 |
| PV | 값 |
| DATETIME1 | DB 입력시각 성격의 timestamp |

즉 **226개 신호가 226개 컬럼으로 저장되는 구조가 아니라, 5개 컬럼의 Long 구조에 TAGNAME별 행이 반복 저장**되는 형태다.

### SCADA SQL 설정과 실제 운영 DB가 달라 보이는 이유

| 구분 | 물리 필드 수 | Tag/변수 수 | 해석 |
|---|---:|---:|---|
| 실제 `suyo.tb_suyo` | 5 | 226 Active | Long Tag History |
| `ELECTRIC_DATA` 설정 | 101 | 전력 100 | SCADA Wide SQL 설정 |
| `OPERATOR_DATA` 설정 | 207 | 공정 206 | SCADA Wide SQL 설정 |
| `SURVEY_DATA` 설정 | 5 | 수질 4 | SCADA Wide SQL 설정 |
| `TMS_DATA` 설정 | 5 | 유량/송풍 4 | SCADA Wide SQL 설정 |
| `water_input` 설정 | 16 | 수질 14 | SCADA Wide SQL 설정 |

`설정이 존재한다`와 `현재 운영 DB에서 실제 테이블로 사용된다`는 같은 의미가 아니다.

## 시간차 원인

분석자료에서는 `DATETIME1 = current_timestamp()` 성격으로 정리되어 있으며 226개 Tag가 순차 INSERT되면서 한 Cycle이 초 경계를 넘는 현상이 관찰되었다.

| 관찰 | 실측 예 | AI 처리 방향 |
|---|---|---|
| 같은 Cycle이 두 초에 걸쳐 저장 | `16:37:32 = 66개`, `16:37:33 = 160개` | Timestamp만으로 Cycle 묶지 않음 |
| Tag 순서 반복 | 최근 완성 Cycle간 `MISMATCH_COUNT=0` | Num/Tag 순서를 복원 보조키로 활용 |
| DB 입력시각 성격 | `DEFAULT current_timestamp()` | `sample_time`과 `received_at` 분리 |

## AI Master DB 제안

Raw 수집 단계:

- `cycle_id`
- `sample_time`
- `received_at`
- `plant_id`
- `source_id`
- `tag_id`
- `value_raw`
- `value_eng`
- `quality`

학습/분석 단계에서는 동일 시간축으로 Pivot한 Wide 구조를 별도 생성한다.

- 현재 운영 DB의 장기간 Schema/Index/부하 조건
