# M203(송풍기) AI 개발 실행순서 및 도구선정

## 결론

M203는 **Signal의 의미를 먼저 고정하고, 그 다음 전체 장기데이터를 일괄 변환**한다. 신규 PLC 직접수집기와 Simulator는 병행하지만 둘 때문에 오프라인 AI 개발을 기다리지 않는다.

```text
Gate 1  M203(송풍기) Signal Master v0.9 + QA  ✅ FROZEN 2026-09-14
   ↓
Gate 2  Rule Book Open Item 병행 정리
   ↓
Gate 3  전체 장기 CLD Batch 변환
   ↓
Gate 4  M203 Master Dataset v0.1
   ↓
Gate 5  전체기간 Baseline
   ↓
Gate 6  XGBoost / LightGBM 머신러닝 회귀모델 비교
   ↓
Gate 7  제약조건 기반 최적화
   ↓
Gate 8  Historical / Shadow Replay
   ↓
M204 → M102 확장
```

## Track A — AI Critical Path

### 1. Signal Master

먼저 `PLC Symbol → PLC 주소 → SCADA Tag → Logger → 단위 → R/W → AI I/O → 안전여부`를 Canonical ID에 묶는다.

완료 전에는 “이 컬럼이 Hz Set인지 실제 Hz인지”, “전력계 계통 Hz인지 인버터 Hz인지” 같은 의미 혼동이 남으므로 전체 Batch 변환을 Freeze하지 않는다.

### 2. Rule Book

M203 Rule Book v1.1의 확인된 Rule을 사용하고 미확정 5개 항목은 Open으로 남긴다. 안전 관련 미확정값을 AI가 임의로 채우지 않는다.

### 3. 전체 장기 Logger 변환

현재 확보된 `2025-09-24 ~ 2026-08-05` 장기 CLD를 전체 처리한다. 원본은 불변 보관한다.

### 4. Master Dataset

AUTO/MANUAL, Fault, Interlock, Stop, 센서이상을 Label로 분리한다. 대표 Logger에 Mode가 없으면 `MODE_UNKNOWN`으로 두며 AUTO로 추정하지 않는다.

### 5. Baseline

AI 전에 다음을 먼저 계산한다.

- DO 구간별 실제 Hz
- Hz 대비 kW
- 유입량 대비 Hz/kW
- 송풍량 대비 Hz/kW
- 같은 DO인데 전력이 다른 구간
- A/B 운전 차이
- AUTO/MANUAL 차이 — 실제 Mode 이력 확보분에 한함
- 시간대/요일 패턴
- Fault/Stop/통신이상 구간

### 6. 전력 예측용 머신러닝 회귀모델

1차 비교는 XGBoost / LightGBM으로 충분하다.

`운전 Hz + RUN + 유입량 + DO + 공정상태 → M203 kW`

동일 Feature/동일 시간분할/동일 평가구간에서 비교한다.

### 7. 제약조건 기반 최적화

예: **DO가 안전범위 아래로 내려가지 않는 조건에서 M203 전력을 최소화할 Hz**를 계산한다.

첫 출력은 제어명령이 아니라 다음과 같은 권고다.

```text
현재 운전 Hz
AI 권고 Hz
예상 kW
예상 절감 kW
예상 DO 범위
제약조건 통과 여부
권고 근거
```

### 8. Shadow Replay

과거 Dataset을 시간순으로 재생하면서 `당시 실제 운전`과 `AI 권고`를 비교한다. PLC Write는 수행하지 않는다.

## Track B — Simulator 병행

Signal Master와 Dataset을 기다리며 놀지 않고 Replay Framework 뼈대를 병행 개발한다.

```text
Replay Clock
Signal Bus
Historical Replay
Actual Operation
AI Recommendation
Compare
```

실제 데이터 연결은 Master Dataset v0.1 이후다. AI 학습과 Simulator는 **같은 Dataset version / Signal Master version**을 사용한다.

## Track C — 신규 PLC Direct Collector 병행

최종 실시간 수집 경로는 다음을 목표로 한다.

```text
A2 PILOT PLC .10 ─┐
                   ├→ Water-AI Data Collector (READ only)
A2O PLC .20 ──────┘
                   ↓
          Raw / Canonical 수집계층
                   ↓
          실시간 AI / Shadow
```

Collector 완성 전에도 기존 Logger로 AI 개발을 진행한다. Collector 가동 후에는 기존 Logger와 동시간 대조해 `PASS / SCALE / DELAY / AVG / MISMATCH / UNKNOWN`으로 신호별 검증한다.

## SQL/SCADA 확인의 위치

- 기존 CIMON/Logger/MySQL: 과거 이력·태그 의미·Scale·저장주기 검증용
- 신규 Collector: 향후 실시간 운영용
- SQL 운영 DB 정상화는 **AI 오프라인 개발의 선행조건이 아니다.**

## 도구 선정

| 목적 | 선정/권고 | 역할 |
|---|---|---|
| 원본 | CLD/CSV 그대로 보존 | 증거/재현 원천 |
| Batch 변환 | Python + Polars | 대량 Logger 처리 |
| 컬럼형 저장 | Parquet + PyArrow | 장기 시계열 Staging/교환 |
| 로컬 분석 | DuckDB | Parquet SQL 조회·Baseline·Replay QA |
| 표/보고 Export | openpyxl/CSV | 사람 검토용 |
| Baseline | Python/Polars/Pandas + matplotlib | 통계/관계 분석 |
| 머신러닝 회귀모델 | scikit-learn + XGBoost + LightGBM | 1차 비교 |
| API/Replay Backend | Python + FastAPI | Simulator/AI 서비스 연계 |
| UI | Water AI Workbench / Electron | Replay/Shadow/운영자 화면 |

> **중요:** DuckDB/Parquet은 개발용 분석 작업공간이다. 프로젝트 공식 원천/Canonical DB 엔진 선택은 별도의 A/B 설계안 및 4인 검토 Gate를 따른다.

## 버전 결합

모든 모델/Replay 결과에는 최소 다음을 남긴다.

```text
signal_master_version
rule_book_version
dataset_version
model_id
model_version
period
feature_list
quality_filter
```

이 정보가 없으면 결과를 공식 비교본으로 승격하지 않는다.
