파이브텍 정수·하수 AI 프로젝트 성격·난이도 및 현재 단계

2026년 9월 11일14 min read

파이브텍 정수·하수 AI 프로젝트 성격·난이도 및 현재 단계

1. 프로젝트 한 줄 정의

이 과제에서 파이브텍 외주 AI 개발 관점의 핵심은 단순한 AI 예측모델 1개 개발이 아니라, 현장 OT 구조를 해석하고 실제 운전데이터를 확보·정합화한 뒤 예측·전력·최적화 모델을 SCADA/PLC 안전계층과 연계하는 산업 OT·데이터·AI 통합 시스템 개발이다.

중요: 아래 난이도 평가는 연구계획서의 공식 등급이 아니라, 지금까지 확보·분석한 현장자료를 바탕으로 한 우리 내부 기술평가다.

2. 난이도 평가

우리 내부 기술평가

종합 난이도: 약 8.5~9 / 10

이 평가는 AI 알고리즘 자체보다 다음 복합 난이도를 포함한다.

  • PLC/XG5000 원본과 실제 운전본 식별
  • HMI/SCADA Tag·Address·Topic·Alarm·Trend 계보 추적
  • Historian 메타 DB와 실제 History Storage 분리구조 해석
  • 장기간 공정 시계열 데이터 확보
  • 정수/하수 서로 다른 공정 모델 개발
  • 운전 Mode·Set Point·RUN/STOP·Fault·Interlock 등 제어문맥 정합화
  • 설비 전력·수질·운전조건의 동시 최적화
  • AI 권고값을 SCADA/PLC 안전조건 아래에서 적용하는 연계구조

즉, 이 프로젝트는 AI 모델 개발 + OT 시스템 리버스 엔지니어링 + 데이터 엔지니어링 + 제어/최적화 + 현장 검증이 동시에 필요한 과제다.

3. 왜 어려운가

중랑 하수

현재까지 확인된 구조는 다음과 같다.

중랑에서는 단순히 DB 컬럼만 보는 것으로 충분하지 않다. PLC 주소 → SCADA Tag → DB 저장값 → 실제 공정 의미 → 운전 Rule을 역추적해야 한다.

특히 A2O PLC와 A2 PILOT PLC의 역할이 다르며, A2 PILOT의 실제 제어 Rule은 원본 프로그램과 운전조건을 확인하기 전에는 확정할 수 없다.

광암 정수

현재까지 규명한 광암 주요 계보는 다음과 같다.

광암에서는 처음에 대용량 WWALMDB가 장기 공정이력 DB처럼 보일 수 있었으나, 분석 결과 Alarm/Event DB로 분리됐다.

또한 Runtime.bak은 Historian의 Tag·Storage 메타정보와 History 조회 인터페이스를 포함하지만, 장기간 공정값 본체가 일반 SQL Table Row 형태로 전부 들어 있는 구조는 아니었다. POS11에서 Runtime.dbo.History 실조회와 StorageLocation 확인까지 진행하여 실제 History Storage 구조를 별도로 확인했다.

이 과정은 일반적인 AI 데이터 전처리보다 산업 시스템 데이터계보 역추적 성격이 강하다.

4. 영역별 난이도

영역내부 난이도현재 판단 이유
PLC / XG5000 분석높음백업·구버전·현행본 구분, 주소·Symbol·Program Block 추적 필요
HMI / InTouch 분석높음Tag, AccessName, Topic, Item, Alarm, Trend, 화면 연결 필요
Historian 분석매우 높음SQL Runtime 메타계층과 실제 History Storage가 분리됨
데이터 정합화매우 높음시간축, 결측, 운전 Mode, 상태변수, Set Point 문맥까지 맞춰야 함
AI 예측중~높음데이터 기반이 정리된 뒤에는 상대적으로 정형화 가능
설비 전력 예측높음RUN/Hz/가동대수/유량/공정조건과 전력을 함께 해석해야 함
제어·최적화 / MPC매우 높음수질·설비·PLC 제약조건을 동시에 만족해야 함
SCADA / PLC 연계매우 높음실제 설비 적용이므로 안전조건·권한·Mode·Fallback 필수
정수/하수 동시 대응매우 높음공정과 주요 변수가 달라 동일 AI 모델을 그대로 사용할 수 없음
현장·문서·기관 조율높음자료가 분산되고 시점·버전·책임경계를 계속 확인해야 함

5. 정수와 하수는 사실상 별도 개발축

중랑 하수 개발축

우선 대상은 송풍기 M203, 내부반송 M204, 유량조정펌프 M102 순으로 검토한다.

광암 정수 개발축

광암은 정수 AI 학습·검증 기준 시설이며, 개발·검증·표준화 후 명장 최종 적용을 목표로 한다.

따라서 “AI 프로젝트 하나를 두 시설에 복사”하는 구조가 아니라, 공통 데이터·연계 아키텍처를 공유하되 정수와 하수의 예측·최적화 모델은 별도로 개발하는 것이 원칙이다.

6. 현재까지 넘어온 단계

시작 시점

현재 확인된 상태

광암에서는 다음이 직접 확인됐다.

  • POS11 Runtime.dbo.History에서 실제 공정 시계열 값 조회 가능
  • WWALMDB는 Alarm/Event DB
  • Runtime은 Historian Tag/Storage 메타 + History 조회 인터페이스
  • 실제 Storage 경로:
    • D:\Historian\Data\Circular
    • R:\Overflow\Data
    • D:\Historian\Data\Buffer
    • D:\Historian\Data\Permanent

다만 장기간 AI 학습용 정식 데이터셋은 아직 우리 측에 인수 완료되지 않았다.

7. 앞으로의 개발 위치

AI 모델 개발은 이 전체 흐름의 중간 단계다. 데이터계보와 운전문맥이 틀리면 이후 모델 정확도가 높아도 현장 적용에는 사용할 수 없다.

8. 현재 가장 큰 3개 리스크

1) 광암 Historian 장기 실제값 확보

현재 확인됨

  • Historian 존재
  • POS11 History 조회 가능
  • 실제 Storage Path 확인

아직 부족함

  • 각 Storage 총용량·파일수
  • 실제 보존기간
  • AI용 장기간 데이터 인수

우리가 해야 할 일

  • Storage 용량 확인
  • 용량 가능 시 원본 Storage 확보
  • 최신 Runtime BAK / Tag 메타 함께 보존
  • 최종 AI 학습본은 History Query Export로 표준화

2) 중랑 A2 PILOT 실제 제어 Rule 확정

현재 확인됨

  • A2O PLC와 A2 PILOT PLC 역할이 다름
  • A2 PILOT를 공정제어 PLC로 봐야 함

추가 확인 필요

  • RUN/STOP
  • AUTO/MANUAL
  • Interlock / Run Permit
  • Timer / Delay
  • 최소·최대 Hz
  • 교번·고장대체 운전
  • DO/MLSS/ORP 등 조건에 따른 실제 Rule

원칙

  • 원본/현장 근거 없이 실제 제어 Rule을 확정하지 않는다.

3) AI 대상 Tag와 운전조건의 Master DB 정리

단순 센서값만 저장하면 부족하다.

9. 프로젝트에서 특히 위험한 오해

가장 큰 관리 리스크는 이 과제가 겉으로는 **“AI 모델 하나 만들면 되는 일”**처럼 보이는 것이다.

실제 구현에는 다음이 모두 필요하다.

따라서 일정과 견적도 AI 모델 코딩 시간만으로 산정하면 안 된다. 데이터 확보·역추적·현장확인·연계검증 시간이 별도 작업으로 관리돼야 한다.

10. 확정 / 추정 / 추가확인 / 개발방향 구분

자료로 확인된 내용

  • 중랑과 광암의 현장 시스템 구조가 서로 다름
  • 광암 InTouch / DeviceXPlorer / Historian 구성 존재
  • 광암 POS11 Runtime.dbo.History 실제 조회 가능
  • 광암 Historian StorageLocation 실제 경로 4개 확인
  • WWALMDB는 Historian 장기 공정값 DB가 아니라 Alarm/Event DB
  • 정수와 하수는 같은 AI 모델을 그대로 사용할 수 없는 공정구조

합리적 추정 / 내부 평가

  • 종합 난이도 8.5~9/10
  • 이 과제를 산업 OT·데이터·AI 통합 프로젝트로 분류
  • 정수/하수 개발축을 사실상 별도 AI 개발축으로 관리하는 것이 적절

추가 확인 필요

  • 광암 History Storage 실제 총용량과 보존기간
  • R: Storage의 물리적 정체
  • 중랑 A2 PILOT 상세 운전 Rule
  • 각 AI 대상 Tag의 최종 데이터 품질·결측률·저장주기
  • 현장 자동제어 허용범위

우리가 제안하는 개발 방향

AI는 PLC를 대체하거나 우회하지 않고, 더 좋은 운전 Set Point를 계산하는 상위 최적화 계층으로 둔다.
