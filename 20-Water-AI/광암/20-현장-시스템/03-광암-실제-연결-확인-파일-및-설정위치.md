# 광암 `PLC → DeviceXPlorer → InTouch → Historian/DB` 실제 연결 확인 위치

## 0. 목적

현재 확보한 `Wonderware.zip`으로 제품 구성과 PLC 통신 대상은 상당 부분 확인했지만, **광암에서 런타임 데이터가 실제로 어느 경로로 흐르는지**는 운영 설정을 대조해야 최종 확정할 수 있다.

XG5000 원본이 확보되었으므로 이제 아래 **5개 연결**을 각각 증명해야 한다.

```text
A0. 현장 신호 → PLC 주소/프로그램/네트워크 전송
A. PLC → DeviceXPlorer
B. DeviceXPlorer → InTouch
C. InTouch → Wonderware Historian
D. InTouch Alarm → WWALMDB
```

그리고 InTouch 자체의 `.LGH/.IDX` Historical Logging이 별도로 사용 중인지도 함께 확인한다.

---


# 1. A0구간 — `현장 신호 → PLC 주소/프로그램/PLC간 전송`

XG5000 `.xgwx` 155개 수집본이 확보되어 이 구간은 이제 파일 기반 분석이 가능하다.

다만 155개에는 동일 PLC의 과거본/수정본/OLD가 포함되어 있으므로 우선 **현장 PLC Canonical ID와 현재본 후보**를 정규화한다.

확인할 항목:

```text
PLC Canonical ID
Project File / Project Name
CPU / Module / Slot
211.x / 212.x IP
Program Block
Symbol / Comment
%IX / %IW / %MX / %MW / %QX 주소
High-speed Link / Network 송수신 영역
AUTO/MANUAL / PID / Interlock / Alarm 관련 로직
```

특히 PCS2↔FCC 24개 구조는 송수신 Word 영역까지 추출하여 통신 Matrix로 만든다.

세부: [[04-광암-PLC-XG5000-구조-및-통신맵]]

# 2. 가장 먼저 확인할 결론 판별표

| 확인 위치 | 봐야 할 값 | 값이 이러면 | 판정 |
|---|---|---|---|
| InTouch `Access Names` | Application Name | `DXPSV` | **DeviceXPlorer → InTouch 직접 DDE/SuiteLink 가능성이 매우 높음** |
| InTouch `Access Names` | Application Name | `FSGateway` 또는 FSGateway 서버명 | **DeviceXPlorer → OPC → FSGateway → InTouch 경유 구조** |
| InTouch `Access Names` | Topic Name | `P1`, `P2`, `P21` 등 DeviceXPlorer Topic과 일치 | 해당 PLC Device와 InTouch 연결 확정 |
| InTouch Tag Dictionary | Access Name + Item Name | Item이 `D...`, `M...` 등 PLC 주소 또는 DXP Tag | **InTouch Tag → PLC 주소** 매핑 확보 |
| Historian SMC `Imported Nodes` | Path | InTouch Application의 `Tagname.x` UNC 경로 | **InTouch → Historian 가져오기 연결** 확인 |
| Historian SMC `InTouch Nodes` | Tag 목록 | InTouch Tag와 일치 | Historian 수집 대상 Tag 확인 |
| Alarm DB Logger Manager | Server / Database | 실제 SQL 서버 + `WWALMDB` | **InTouch Alarm → WWALMDB** 연결 확정 |
| InTouch Historical Logging | Log Data / 저장 폴더 | 활성 + `.LGH/.IDX` 존재 | InTouch 자체 History도 별도 운용 중 |

# 3. A구간 — `PLC → DeviceXPlorer` 확인

## 2.1 현재 확보한 설정 파일

제공 자료 기준:

```text
Wonderware/InTouch/DXPSV.dxp
```

이 파일에서 직접 확인된 값:

```text
DeviceXPlorer 5 Configuration File
ProductVersion = 5.4.0.1
LibType = LsisEthernet
Local-side setting = 192.9.211.120
Remote PLC = 192.9.211.10 / .12 / .14 / .16 / .18 / .21 / .22 / .23 / .25 / .26 / .28 / .30 / .32
Remote TCP Port = 2004
```

### 현장 PC에서 확인할 것

1. `DXPSV.dxp`가 **실제 런타임에서 사용하는 프로젝트 파일인지** 확인
2. DeviceXPlorer 실행 화면에서 Port/Device가 동일한지 확인
3. 각 Device 통신 상태가 정상인지 확인
4. PC NIC 주소가 `192.9.211.120`인지 확인

### 파일 검색

운영 PC에서 파일 위치가 다를 수 있으므로 `Wonderware.zip`의 경로를 그대로 운영 경로라고 가정하지 않는다.

PowerShell 예시:

```powershell
Get-ChildItem C:\ -Filter DXPSV.dxp -File -Recurse -ErrorAction SilentlyContinue |
  Select-Object FullName, LastWriteTime, Length
```

네트워크 설정 확인:

```powershell
Get-NetIPAddress -AddressFamily IPv4 |
  Select-Object InterfaceAlias, IPAddress, PrefixLength
```

### 확인 완료 기준

```text
DXPSV.dxp의 Device/Port 설정
+
실제 DeviceXPlorer 런타임 설정
+
PC NIC
+
PLC Ping/통신 상태
```

이 4개가 일치하면 `PLC → DeviceXPlorer` 구간은 확정한다.

# 4. B구간 — `DeviceXPlorer → InTouch` 확인

## 3.1 가장 중요한 설정: DeviceXPlorer DDE/SuiteLink

TAKEBISHI DeviceXPlorer Ver.5는 Wonderware InTouch와 **DDE/SuiteLink로 직접 연결할 수 있다.**

DeviceXPlorer Ver.5의 기본 SuiteLink Application Name은:

```text
DXPSV
```

DeviceXPlorer에서 확인 위치:

```text
Tools
→ Options / Common Properties
→ DDE/SuiteLink
→ Application Name
```

각 Device에서 확인 위치:

```text
Device Options
→ DDE/SuiteLink Enable
→ Topic Name
→ Update Cycle
```

기본적으로 Topic은 Device 이름을 사용할 수 있으며, 실제 값은 GUI에서 확인한다.

## 3.2 InTouch에서 확인 위치

### InTouch Application 실제 폴더 찾기

**Application Manager**에서 등록된 Application의 경로를 먼저 확인한다.

InTouch 문서의 기본 예시는 사용자 Documents 아래 `My InTouch Applications`이지만, 광암 운영 서버는 임의 경로일 수 있으므로 **Application Manager에 표시되는 실제 경로를 기준**으로 한다.

운영 PC에서 검색할 핵심 파일:

```text
INTOUCH.ini
Tagname.x
*.win
```

PowerShell 예시:

```powershell
Get-ChildItem C:\ -Filter Tagname.x -File -Recurse -ErrorAction SilentlyContinue |
  Select-Object FullName, LastWriteTime, Length

Get-ChildItem C:\ -Filter INTOUCH.ini -File -Recurse -ErrorAction SilentlyContinue |
  Select-Object FullName, LastWriteTime, Length
```

## 3.3 Access Name 확인

WindowMaker에서:

```text
Special
→ Access Names
```

확인할 필드:

```text
Access Name
Node Name
Application Name
Topic Name
Protocol
Primary/Secondary Source
```

### 광암에서 제일 먼저 볼 값

```text
Application Name = DXPSV ?
```

**`DXPSV`이면 TAKEBISHI DeviceXPlorer Ver.5의 기본 SuiteLink 서버명과 일치한다.**

그 다음:

```text
Topic Name = P1 / P2 / P4 / P6 / P7 / P8 / P21 / P22 / P23 / P25 / P26 / P27 / P30 ?
```

을 확인한다.

> Topic이 설비명이나 다른 사용자 정의 문자열일 수도 있으므로 DeviceXPlorer Device Options의 Topic Name과 1:1 비교한다.

## 3.4 Tag Dictionary에서 실제 PLC 주소 확인

WindowMaker:

```text
Special
→ Tagname Dictionary
```

각 I/O Tag에서 확인할 핵심 필드:

```text
Tag Name
Tag Type (I/O Real / I/O Integer / I/O Discrete ...)
Access Name
Item Name
Log Data
Alarm 설정
```

실제 연결은 다음 식으로 복원한다.

```text
InTouch Tag
→ Access Name
→ Application = DXPSV
→ Topic = DeviceXPlorer Device/Topic
→ Item Name = DeviceXPlorer Tag 또는 PLC 동적 주소
→ PLC
```

### 매우 중요 — 광암 `DXPSV.dxp`에 Tag가 거의 없는 이유

현재 `DXPSV.dxp` XML에는:

```text
DEVICE : 13개 설비 + SYSTEM
정적 <TAG> 정의 : 1개
EnableUnknownItemID = 1
AutoAddItem = 0
```

만 확인된다.

TAKEBISHI 공식 가이드에서는 InTouch Item Name에 DeviceXPlorer의 정적 Tag 이름뿐 아니라 **PLC 디바이스 주소를 동적으로 직접 지정**할 수 있다고 설명한다.

예:

```text
M100
D123
```

따라서 광암은 **PLC 주소가 `DXPSV.dxp`에 전부 저장되어 있지 않고 InTouch Tag Dictionary의 `Item Name`에 대량으로 존재할 가능성**이 있다.

현재 상태에서는 이 부분을 **강한 추정**으로 두고, DBDump로 확정한다.

## 3.5 가장 좋은 확보 방법 — DBDump

InTouch Application Manager에서 해당 Application을 선택하고 **DBDump**를 실행한다.

DBDump CSV에는 다음이 포함된다.

```text
:IOAccess    ← Access Name 정의
Tag records  ← Tag Name / Access Name / Item Name / Logged 등
```

따라서 **광암 PLC 매핑 분석에 가장 가치가 높은 단일 파일은 InTouch DBDump CSV**다.

### 확보 요청 파일

```text
GW_InTouch_DBDump.csv
```

이 파일 하나로 다음을 대량 자동 매핑할 수 있다.

```text
InTouch Tag
→ Access Name
→ Application
→ Topic
→ Item Name
```

# 5. `FSGateway`를 실제로 쓰는지 판별하는 방법

제공 자료에는:

```text
Wonderware/DAServer/FSGateway/Bin/FSGateway.exe
```

가 존재한다.

그러나 설치 파일 존재만으로 런타임 사용을 확정하지 않는다.

## 4.1 판별 우선순위

### 1차 — InTouch Access Name

```text
Application Name = DXPSV
```

이면 **DeviceXPlorer 직접 SuiteLink 연결** 쪽이 우선이다.

반대로:

```text
Application Name = FSGateway 계열
```

이면 Gateway 경유 가능성이 높다.

### 2차 — Wonderware SMC / DAServer Manager

FSGateway 구성에서 아래가 실제 활성화되어 있는지 확인한다.

```text
OPC Server Object
OPC Group
DeviceXPlorer OPC ProgID/Server
활성 상태
```

### 3차 — 프로세스/서비스

```powershell
Get-Process | Where-Object {
  $_.ProcessName -match 'DXP|FSGateway|view|wm|aah'
} | Select-Object ProcessName, Id, Path

Get-Service | Where-Object {
  $_.DisplayName -match 'DeviceX|Wonderware|Historian|ArchestrA|Gateway'
} | Select-Object Status, Name, DisplayName
```

> `FSGateway.exe`가 실행 중이어도 다른 용도로 쓰일 수 있으므로 **InTouch Access Name + FSGateway 설정**까지 같이 봐야 한다.

# 6. C구간 — `InTouch → Wonderware Historian` 확인

## 5.1 Historian에서 가장 강한 증거

Wonderware Historian 11.6 계열은 InTouch Data Dictionary를 가져올 수 있으며, SMC에서 **Imported InTouch Node**와 원본 `Tagname.x` 경로를 확인할 수 있다.

System Management Console에서:

```text
Historian
→ Historian Group
→ [광암 Historian Server]
→ Configuration Editor
→ System Configuration
→ Storage
→ Imported Nodes
```

Imported Node의 Properties에서 확인:

```text
Machine Name
Path = InTouch Tagname.x의 UNC 경로
InTouch Node Key
```

여기서 `Path`가 광암 InTouch Application의 `Tagname.x`를 가리키면 **InTouch ↔ Historian 구성 연결은 사실상 확정**할 수 있다.

## 5.2 Historian에 들어간 InTouch Tag 확인

SMC:

```text
Configuration Editor
→ Public Groups
→ InTouch Nodes
→ [광암 InTouch Node]
```

또는:

```text
Configuration Editor
→ System Configuration
→ Tag Configuration
→ Analog Tags / Discrete Tags / String Tags
```

확인할 것:

```text
Historian Tag Name
InTouch Tag Name
Description
Acquisition
Storage
Deadband
Current Editor
```

Historian 11.6 문서상 InTouch에서 Import된 Tag는 `Current Editor = InTouch`로 식별할 수 있다.

## 5.3 Runtime DB에서도 확인 가능

Historian 설정 메타데이터는 SQL Server의 **Runtime DB**에서 다음 계열 테이블로 확인할 수 있다.

```text
Tag
AnalogTag
DiscreteTag
StringTag
```

> 이 `Runtime` DB는 Historian의 **Tag/설정 메타데이터**를 보는 용도다. 장기간의 실제 시계열 값 전체가 일반 SQL 테이블에 그대로 누적되는 구조라고 이해하면 안 된다.

## 5.4 실제 Historian 데이터 파일 위치 확인

SMC:

```text
Configuration Editor
→ System Configuration
→ Storage
→ Storage Locations
```

여기서 실제 Path를 기록한다.

또한:

```text
Management Console
→ History Blocks
```

에서 기간별 History Block과 Location을 확인한다.

확보할 값:

```text
Circular Storage Path
Alternate Storage Path
Buffer Storage Path
Permanent Storage Path
History Block Start/End Time
```

### 주의

예제 경로 `C:\Historian\Data\Circular` 등을 광암의 실제 경로로 기록하면 안 된다. **SMC에 표시된 광암 서버의 실제 Path만 확정값으로 사용한다.**

# 7. InTouch 자체 Historical Logging도 반드시 확인

Wonderware Historian과 별개로 InTouch는 자체 Historical Logger를 사용해:

```text
*.LGH
*.IDX
```

파일을 만들 수 있다.

WindowMaker:

```text
Tools view
→ Configure
→ Historical Logging
```

확인할 값:

```text
Enable Historical Logging
Keep Log Files for N days
Store Log Files in Application Directory
또는 특정 Directory
```

각 Tag:

```text
Tagname Dictionary
→ Log Data
→ Log Deadband
```

### 왜 확인해야 하나

광암에서 과거 공정이력이 있다고 해도 그것이 반드시 Historian Server에만 있는 것은 아니다.

가능한 형태:

```text
1. Historian Server만 사용
2. InTouch LGH/IDX만 사용
3. 둘 다 사용
```

따라서 `.LGH/.IDX` 존재 여부도 조사한다.

PowerShell:

```powershell
Get-ChildItem C:\ -Include *.lgh,*.idx -File -Recurse -ErrorAction SilentlyContinue |
  Select-Object FullName, LastWriteTime, Length
```

# 8. D구간 — `InTouch Alarm → WWALMDB` 확인

## 7.1 Alarm DB Logger Manager

InTouch Tools view:

```text
Applications
→ Alarm DB Logger Manager
→ Settings
```

확인할 값:

```text
Server Name
Database
User Name
Logging Mode = Detailed / Consolidated
Alarm Query
Priority Range
Logging Interval
Service 실행 여부
```

여기서:

```text
Database = WWALMDB
```

이고 Server Name이 현재 확보한 MSSQL BAK의 원본 서버와 일치하면 연결이 확정된다.

제공 자료 내 관련 실행 파일:

```text
Wonderware/InTouch/wwalmlogger.exe
Wonderware/InTouch/almlogwiz.exe
Wonderware/InTouch/WWAlmPurgeService.exe
```

## 7.2 Alarm DB Query도 기록

예시 형식:

```text
\\NodeName\Provider!AlarmGroup
\Provider!AlarmGroup
```

광암에서 실제 Query를 확보하면 **어느 InTouch Node/Alarm Group의 알람을 WWALMDB에 넣는지**까지 알 수 있다.

# 9. 광암에서 현장 엔지니어에게 받아야 할 최소 자료

우선순위 순서다.

| 우선순위 | 자료 | 이유 |
|---:|---|---|
| 1 | **InTouch DBDump CSV** | Access Name + Item Name으로 PLC 주소 매핑 핵심 |
| 2 | **InTouch Application 전체 ZIP** | `Tagname.x`, `INTOUCH.ini`, Window/Script/설정 전체 확보 |
| 3 | DeviceXPlorer DDE/SuiteLink 설정 화면 + 현재 사용 `.dxp` | Application/Topic/Device 실제값 확정 |
| 4 | Historian SMC `Imported Nodes`, `InTouch Nodes`, `Tag Configuration` Export/화면 | InTouch→Historian 연결 및 Tag 수집 대상 확정 |
| 5 | Historian `Storage Locations`, `History Blocks` 화면 | 실제 데이터 위치와 보존기간 확인 |
| 6 | Alarm DB Logger Manager 설정 화면 | WWALMDB SQL Server/DB/Query 확정 |
| 7 | `.LGH/.IDX` 파일 목록 | InTouch 자체 History 사용 여부 확인 |

# 10. 확보 후 만들 최종 매핑표

최종 목표는 다음 컬럼을 한 행으로 연결하는 것이다.

| 설비 | PLC IP | DXP Device | DXP Topic | InTouch Access Name | InTouch Tag | Item/PLC 주소 | Historian Tag | Historian 저장 | Alarm 여부 | WWALMDB |
|---|---|---|---|---|---|---|---|---|---|---|
| 예 | 192.9.211.10 | P1 | P1 또는 설정값 | ... | ... | D123 | ... | Yes | Yes | Yes |

이 표가 완성되면 광암의 실제 AS-IS 데이터 수집 구조가 확정된다.

# 11. 현 시점 판정

```text
현장 신호 → PLC 내부주소 : XG5000 원본 분석 가능 / 현재 운전본 정규화 필요
PLC → DeviceXPlorer       : 설정 근거 매우 강함 / XG5000 IP 대조로 추가 확정 가능
DeviceXPlorer → InTouch   : 직접 SuiteLink 가능성이 높음, Access Name 미확보로 최종 미확정
FSGateway 경유            : 설치는 확인, 실제 경유 여부 미확정
InTouch → Historian       : 제품 구성 확인, Imported Node/Tag 설정 미확보로 미확정
InTouch → WWALMDB         : WWALMDB 스키마 + Alarm DB 구성으로 강한 확정 수준, Logger 설정으로 최종 확정 필요
InTouch → LGH/IDX         : 사용 여부 미확정
```

## 2026-09-09 수집 완료 상태

기존 체크리스트 중 다음은 더 이상 '미확보'가 아니다.

```text
현재 InTouch DBDump       → DB_20260518.CSV 확보
현재 dde.cfg              → 2026-06-22 확보
현재 tagname.x            → 2026-06-22 확보
Historian Export          → historian.txt(2022-12-06) 확보
```

현재 1순위 미확정은 다음으로 다시 좁혀졌다.

1. **4개 Historian Storage 경로의 실제 용량/파일수 확인 및 원본 확보 가능성 판단**
2. `R:\Overflow\Data`가 로컬/매핑/별도 Storage인지 확인
3. **현재 GFENet Application의 실제 실행 프로세스/제품 정체**
4. **GFENet ↔ DeviceXPlorer 관계**
5. **XG5000 Online Compare로 현행 PLC 프로젝트 확정**
6. **DDE Item(MW주소) ↔ XG5000 Symbol/Program Block JOIN**


## 2026-09-09 DB 백업 분석 완료 반영

추가로 다음 BAK는 이제 “정체 미확정”이 아니다.

```text
Runtime.bak  → 원래 DB = Runtime / Historian 메타 DB
backup2.bak  → 원래 DB = Runtime / 2026-07-23 최신 백업
Holding.bak  → 원래 DB = Holding / 주요 테이블 0건
```

최신 Runtime에는 `StorageLocation.Path` 컬럼이 실제 존재한다. 다음 SQL 조회를 현장에서 직접 수행하면 현재 Storage 경로를 재확인할 수 있다.

```sql
SELECT * FROM Runtime.dbo.StorageNode;
SELECT * FROM Runtime.dbo.StorageLocation ORDER BY StorageType, SortOrder;
SELECT * FROM Runtime.dbo.IOServer;
SELECT * FROM Runtime.dbo.Topic;
```

이후 해당 `Path`의 **실제 History Storage 파일**을 확보하거나 Historian Query/Export로 장기 값을 추출한다.


# 2026-09-09 Historian 실제 저장파일 현장 확보 추가 확인

현장시간이 짧으므로 **POS11에서 장기 SQL Export를 먼저 수행하기보다 실제 History Storage 위치와 크기를 빠르게 확인**한다.

## SQL로 저장위치 확인

```sql
USE Runtime;
SELECT * FROM dbo.StorageLocation;
SELECT * FROM dbo.StorageNode;
```

2026-09-09 현재 직접조회로 다음 값이 확인됐다.

```text
D:\Historian\Data\Circular
R:\Overflow\Data
D:\Historian\Data\Buffer
D:\Historian\Data\Permanent
StorageNode = POS11
```

따라서 Path 미확정 항목은 해소되었다. 다음은 실제 용량/파일수와 `R:`의 물리적 정체 확인이다.

## PowerShell로 용량 확인

```powershell
$Path = "<StorageLocation.Path에서 확인한 상위경로>"
$files = Get-ChildItem -LiteralPath $Path -File -Recurse -ErrorAction SilentlyContinue
$bytes = ($files | Measure-Object Length -Sum).Sum
[PSCustomObject]@{
  Path=$Path
  GB=[math]::Round($bytes/1GB,2)
  TB=[math]::Round($bytes/1TB,3)
  Files=$files.Count
}
```

용량이 이동매체로 감당 가능하면 **History Storage 원본 + 최신 Runtime BAK + StorageLocation/StorageNode 결과를 세트로 확보**하는 방향을 우선 검토한다.

단, 운영 중 Storage의 단순 복사가 정합성 있는 백업을 보장하는지는 추가 확인이 필요하므로, 실제 복사 전에 현장 담당자에게 정식 Backup/Snapshot 방식 또는 운영 중 복제 가능 여부를 확인한다. Historian/SQL 서비스를 임의 중지하지 않는다.
